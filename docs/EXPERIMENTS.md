# 實驗紀錄：新車損快速分類器

目標：輸入同一台車、同一個角度的**取車照與還車照**，輸出「這次租車產生新車損」的分數；分數超過門檻就轉人工，低於門檻就自動放行。我們想找的是 AUC 最高、每對耗時最短的方法。

- 硬體：一張 RTX 4070 Ti SUPER（16 GB），Windows 11，PyTorch 2.14（CUDA 12.6），transformers 5.18。
- 所有推論都在本機，沒有使用任何雲端 API。
- 每對秒數**包含讀圖**。

## 1. 評估設計

| 代號 | 資料 | 標籤 | 用途 |
|---|---|---|---|
| **E1** | 官方的 141 對取車／還車照片：索賠 21 對、正常 120 對，共 50 台車 | 真標籤（有沒有索賠） | 主要指標 |
| E2 | 官方 500 組補充照片的四角配對 | 弱標籤：還車時才有、模型確認是車損的近拍 | 一致性檢查（只有 12 個正例） |
| E3 | 主辦單位上傳清單裡，同一台車連續兩筆訂單的四角配對 | 弱標籤：後一筆訂單才出現車損近拍 | 一致性檢查（32 個正例） |

- **信賴區間**：以「車」為單位做 bootstrap，因為同一台車的照片彼此不獨立。方法之間的比較一律用**配對 bootstrap**，在同一批車上算 AUC 差值的 CI。
- **對照組**（每個 VLM 都跑）：
  - **P1S（照片對調）**：如果模型真的在比對前後，對調後索賠對的分數應該下降。
  - **P6（同一張還車照放兩次）**：兩張一樣，應該回答「沒有新傷」。
  - **P4（只看還車照）**、**P5（只看取車照）**：用來拆解分數主要來自哪一張照片。
- **捷徑檢查**：
  - 只看檔案資訊（尺寸、副檔名、檔案大小）的邏輯迴歸（`metadata_baseline.py`）。
  - 標籤打亂後重新訓練（`finetune_classifier.py --perms`）。
- **重疊檢查**：
  - 三個資料來源之間沒有完全相同的檔案（MD5 比對）。
  - 上傳清單的部分用車牌排除了 E1 的車（找到 1 台、2 對，已移除）。
  - 500 組補充照片沒有車牌資訊，無法確認車輛不重疊。

## 2. Jev 式讀法（不生成文字，讀答案 token 的機率）

所有 VLM 用同一套問法（原文是英文，以下是中譯）：

- **P1**：「兩張照片是同一台車的同一個角落，A 是取車時拍的，B 是還車時拍的。這次租車期間，車身有沒有出現 B 看得到、A 看不到的**新**損傷？A 已經有的舊傷不算，光線、反光、髒汙、水滴、陰影、角度差異也不算。只回答 Yes 或 No。」
- **P2**：同一題的中文版。
- **P3**：逐部位比對的版本。

分數 = log P(Yes) − log P(No)，在答案位置做**一次前向**，`logits_to_keep=1`。

- **P1–P3 是事先定好的**，主要分數取三者平均。
- 「只用 P1」是看過 E1 結果後，為了速度才改用的；P1 的 AUC 比三者平均略低，所以這個選擇是偏保守的。

**表格說明：**
- 「原始解析度」是指前處理不縮圖：長邊 1280 或 800。
- 「抓全部 21 對時轉人工比例」是把門檻設在分數最低的那一對索賠，再算 141 對裡有多少比例超過門檻。這個門檻是看過答案才設的，所以是最樂觀的情況；而且 E1 有 15% 是索賠，比真實流量高。
- 表中的 AUC、轉人工比例與秒數，以及下面引用的配對差值，都由 `experiments/final_summary.py` 從同一份分數快取彙總，結果在 `results/final_summary.json`。秒數只平均 E1 的 141 對。

### 重點

1. **在原始解析度下，VLM 用 Jev 式讀法高於訓練出來的影像分類器**：
   - 4B（P1，0.954）− ConvNeXt 凍結＋LR（0.840）= **+0.113** [+0.02, +0.22]。
   - 4B − CLIP 1−cos（0.837）= **+0.117** [+0.02, +0.23]。
   - 原始解析度是比較 4 種後選的。在 512／768／1024 下，4B P1 − ConvNeXt 分別是 +0.058 [−0.08, +0.18]、+0.098 [−0.01, +0.21]、+0.076 [−0.05, +0.19]：方向相同，但信賴區間包含 0。
2. **原始解析度最好，但證據有限**：
   - 4B 原始 − 1024 = +0.047 [−0.003, +0.12]，p ≈ 0.09，不顯著。
   - 2B、9B 的方向一致。
   - 解析度是比較過 4 種才選定的，所以數字可能偏樂觀。
3. **更大的模型沒有更好。**9B、Gemma 4 12B、Qwen3-VL-8B、GLM-4.6V-Flash 都沒有贏過 4B。我們也查過 2026 年的公開排行榜：16 GB 放得下、可商用的模型裡，沒有公開證據顯示誰的視覺能力明確優於 Qwen3.5-4B。
4. **別人訓練好的 Jev-like 模型沒有帶來增益**：AUC 打平。imajev 慢 2–3 倍，Intern、vev 跟 4B 差不多；三者照片對調後分數都偏高（0.72–0.85），比較不會分辨哪張是取車照。
5. **自訓學生**：
   - 跟老師（4B P1）相差 −0.012 [−0.04, +0.01]，速度快 1.6 倍。
   - 比未訓練的 0.8B（同樣原始解析度、P1）高 +0.042 [−0.01, +0.11]，不顯著。
   - 照片對調後的 AUC 從 0.74 掉到 0.35：分數對照片順序變得敏感。
   - 但兩張照片相同時 AUC 仍有 0.805（老師是 0.602），所以還不能說它學會了排除舊傷。

## 4. 對照組怎麼解讀（4B，原始解析度）

| 輸入 | AUC |
|---|---|
| 取車照 + 還車照（P1） | 0.954 |
| 只看還車照（P4） | 0.942 |
| 只看取車照（P5） | 0.53 |
| 照片對調（P1S） | 0.49 |
| 同一張還車照放兩次（P6） | 0.60（回答 Yes：0/141） |

- **分數主要來自還車照**。P1 − P4 = +0.012 [−0.03, +0.06]，加入取車照的增益在這批資料上還不顯著。
- 「照片對調後 0.49」和「只看取車照 0.53」幾乎一樣，所以它也符合「只看第二張照片」的解釋，不能單獨當比對的證據。
- **取車照確實會影響「是不是新傷」的判斷**：
  - 同一張照片放兩次時，141 對一律回答「沒有新傷」。
  - 取車照本來就有傷的正常配對（模型判斷，15 對）：只看還車照時有 10 對被判有傷，兩張一起看降到 3 對。
- **只看取車照分不出哪些是索賠（0.53）**，沒有證據顯示「索賠資料夾的拍攝批次」是分數的主要來源。

## 5. 真實流量的轉人工比例

門檻用 4B（原始解析度、P1）設定在「21 對已知索賠全部抓到」，再套到 3,850 對**無標註**配對上。這 3,850 對包括：
- 1,352 對來自 500 組補充照片，是真正的取車照對還車照，轉人工 18.6%。
- 2,498 對來自上傳清單，是同一台車相鄰兩筆訂單的還車照，轉人工 16.1%。


| 計算單位 | 轉人工比例 |
|---|---|
| 單一角落配對 | 17% |
| 一整筆還車（四個角齊全，任一角超過門檻就算） | 48%（414 筆）；只算 500 組的 338 筆是 50% |
| E1 的 120 對正常配對 | 23% |

使用這組數字時要注意：
- 門檻是由一對索賠決定的；對新案件，期望召回約 95%，單側 95% 下界是 86.7%。
- 真實流量裡本來就有真的新傷，這些也算在人工比例裡。
- 小刮痕還沒有驗證過。

## 6. 弱標籤（E2/E3）：分不出方法的好壞

| 方法（P1） | E2（12 正 / 150 負） | E3（32 正 / 200 負） |
|---|---|---|
| 4B，1024 | 0.57 | 0.65 |
| 4B，原始解析度 | 0.52 | 0.64 |
| 2B，原始解析度 | 0.43 | 0.67 |
| Gemma 4 12B | 0.51 | 0.63 |

- E2 落在 0.43–0.57（±0.15），E3 落在 0.63–0.67（±0.1），信賴區間大幅重疊。
- 判斷近拍是不是車損的模型，就是 Qwen3.5-4B（1024 解析度）；它跟被評估的方法是同一家族。
- 「客人拍了車損近拍」不等於「這次的新傷」：可能只是在記錄舊傷，傷也可能在沒配對到的角落。所以這種弱標籤的雜訊太大。
- 下一步需要人工標註更多真標籤。

## 7. 沒有效果的嘗試

- **分塊放大**：把取車照和還車照切成上下兩塊、放大後各問一次。
  - 在 1024 解析度時，從 0.917 提升到 0.944，成本約 3 倍。
  - 在原始解析度時是 0.959，每對 2.94 秒，成本約 5.5 倍。
  - 原始解析度直接跑一次就有 0.954，所以淘汰。
- **差值分數**：例如「正向 − 照片對調」、扣掉同一張照片的偏差，都沒有比較好。
- **4B + 9B 集成**：沒有比較好，兩者分數的相關係數是 0.915。

## 8. 傳統影像分類器的補充

- 索賠的 21 對全部是 .jpg，正常的 120 對有三分之二是 .jfif，所以只看副檔名就有 AUC 0.83（`metadata_baseline.py`）。但影像模型讀不到副檔名，這只能說明資料裡有這種捷徑，不能證明分類器用了它。
- 在「兩張都是 .jpg、1280×720」的子集上，訓練分類器是 0.44–0.72（`compare_pairs.py`）。但這個子集的負例只來自 7 台車，信賴區間約 ±0.25。
- 標籤打亂只跑了 2 次（0.65、0.41），還不足以建立隨機情況的分布。
- 結論：**無法確認這些分類器是在看車損**，而且它們沒有贏過不需要訓練的 CLIP 1−cos。

## 9. 驗證後修正的錯誤

主要結論都經過三個獨立的 AI 審查代理，從原始分數重算、專門找漏洞。修正如下：

- 「整筆還車轉人工 31%」改為 **48–50%**。原本的分母大多是缺角的還車單位，四個角都齊的很少，導致低估。
- 成本：0.962 對應的是三個問法平均（每對 1.57 秒）；0.53 秒對應的是只用 P1 的 0.954。集成每對約 7.9 秒，不是 2.7 秒。
- 比較表程式原本的標籤沒有包含解析度，不同解析度的結果會互相覆蓋；已修正，數字以 `final_summary.json` 為準。
- 「訓練分類器主要在學格式捷徑」講過頭了，改成上面第 8 節的寫法。
- 「加入取車照的增益 +0.02」原本是拿三問法平均和 P4 比；跟 P1 比應該是 +0.012。
- 「明顯贏過訓練分類器」只在原始解析度下顯著，已經補上其他解析度的結果。
- 「蒸餾提升 +0.09」原本混入了問法與解析度的差異；在同一個問法、同樣的原始解析度下比較，是 +0.042。
- 弱標籤 E3 與蒸餾訓練池有 195/703 對共用照片（相鄰訂單共用還車照），所以學生在 E3 的分數不採用；E1 不受影響。
